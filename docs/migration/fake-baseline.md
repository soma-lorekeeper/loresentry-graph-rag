# 갱신안 생성 골격과 fake 구현 현황

[LOREKEEPER-625](https://lorekeepers.atlassian.net/browse/LOREKEEPER-625)의 범위는
내부 로직의 입출력 골격과 외부 IO fake를 먼저 만들고, 실행 순서와 실패 흐름을 검증하는 것이다.
실제 업무 판단과 갱신안 생성 품질은 아직 구현·검증하지 않았다. HTTP 라우트나 Kafka 소비자에 연결하지 않았다.

기존 `refresh-mvp.md`는 전체 MVP 계획이며, 이 문서는 그중 먼저 구현한 범위의 현재 상태를 관리한다.

## 구현 위치와 상태

| 위치 | 현재 구현 | 후속 구현 |
|---|---|---|
| [models.py](../../app/refresh/models.py) | 요청·문서·관계·근거·후보·결과·작업 상태의 frozen dataclass와 enum | 외부 스키마와 매핑, 필드별 업무 검증 |
| [ports.py](../../app/refresh/ports.py) | S3 자료, 관계, Content, LLM, 작업 상태, 완료 발행의 여섯 Protocol | 운영 어댑터, 인증·권한·직렬화·실제 저장 |
| [rules.py](../../app/refresh/rules.py) | 입력 검증, 자료 선택, 자료 조합, 청킹, 문맥, 프롬프트, 결과 검증의 입출력 골격 | 기존 AI 부품 선별 이전과 순수 정책 구현 |
| [service.py](../../app/refresh/service.py) | IO와 판단 호출 순서, 조회 생략, 결과 재사용, 실패 중단·재개 | 운영 소비 루프·실행권 복구와 통합 |
| [refresh fake](../../tests/fakes/refresh.py) | 상태가 있는 메모리 저장소와 고정 조회·모델·발행 결과, 오류 주입 | 같은 계약의 실제 어댑터 검증 |
| [내부 stub](../../tests/fakes/rules.py) | 테스트에서 지정한 선택·스냅샷·결과 반환 | stub을 대체하는 실제 업무 판단과 정책별 단위 테스트 |

`RefreshRules`의 모든 기본 메서드는 `RulesNotImplemented`를 발생시킨다.
이 오류는 정상 실패 결과로도 변환하지 않고 호출자에게 전파한다. 성공 이벤트를 보내지 않는다.
`ScriptedRules`는 테스트가 명시적으로 주입하며 운영 코드에서 import하지 않는다.

외부 IO fake는 실제 어댑터와 같은 포트를 구현한다. 내부 stub은 업무 로직이 완성됐다고
가정하기 위한 테스트 전용 응답이다. 현재 성공 시나리오는 두 종류의 대체 구현을 함께 사용한다.

## 실행 순서

1. 전달 계층이 공급한 실행 ID로 작업을 접수한다. 동일 요청의 입력이 다르면 충돌하고, 실행 중이면 다른 실행을 거절한다.
2. 저장 결과가 있으면 다시 생성하지 않는다. 완료 기록까지 있으면 이미 발행된 결과를 반환한다.
3. 고정 실행 스냅샷이 없으면 입력을 읽고 입력 검증 단계를 호출한다.
4. 자동 선택 경로에서 관계를 조회한다. `WAITING`·`UNKNOWN`이면 LLM을 호출하지 않고 재시도 가능한 오류로 중단한다.
5. 자료 선택 단계가 반환한 부족 문서 ID만 Content 포트로 조회한다. 명시적 대상과 자료가 충분하면 관계·추가 조회를 생략할 수 있다.
6. 자료 조합 단계의 실행 스냅샷을 저장하고 작업에 참조를 기록한 뒤 청킹·문맥·프롬프트 단계를 호출한다.
7. LLM 후보를 받아 결과 검증 단계를 호출한다. 결과를 저장하고 작업에 참조를 기록한 뒤 완료를 발행한다.

자료 선택·접근 범위·근거 유효성 자체는 내부 stub이 지정한 응답으로 통과하거나 거절한다.
예를 들어 `BAD_FIELD` 테스트는 실제 필드 검사 알고리즘의 정확성보다 거절 후 성공 제안이 발행되지 않는 흐름을 검증한다.

포트는 현재 동기 메서드다. 이후 비동기 소비자와 연결할 때 블로킹 IO가 이벤트 루프를 막지 않도록
호출 방식을 결정해야 한다. 생성자 주입 경계는 유지하며 범용 명령 실행기는 도입하지 않았다.

## fake와 fixture 사용

실행 방법은 [테스트 안내](../../tests/refresh/README.md)를 따른다.
`tests/fakes/fixtures.py`의 `example()`은 변경 원고 1개, 관련 설정 1개, 관계 1개와 제안 1개를 만든다.
ID·revision·본문·근거 위치가 고정돼 있으며 외부 데이터나 현재 시각에 의존하지 않는다.
실제 S3 JSON 형식이나 LLM 품질 평가 데이터로 확정한 것은 아니다.

`tests/fakes/scenario.py`의 `scenario()`는 각 테스트에 독립적인 여섯 fake와 내부 stub을 만든다.
같은 `Calls` 객체로 호출 순서·인자를 기록하고, `failures[연산명]` 큐에 예외를 넣어 해당 호출을 실패시킨다.
큐의 `None`은 그 호출을 통과시키므로 두 번째 checkpoint 실패도 재현할 수 있다.
발행 전 실패와 발행 후 응답 유실은 각각 `publisher.publish`, `publisher.ack`로 구분한다.

## 실패와 복구의 검증 범위

| 상황 | 현재 동작·검증 |
|---|---|
| 미구현 판단 또는 예상하지 못한 코드 오류 | 오류를 전파하고 성공 완료를 발행하지 않음 |
| 재시도 가능한 IO 오류 | 실행권을 반환하고 호출자에게 전파. 서비스 내부 자동 재시도 없음 |
| 명시적 업무 거절·영구 입력 오류 | `FAILED` 결과를 저장·발행. 작업의 `COMPLETED`는 성공 제안이 아니라 처리 종료를 뜻함 |
| 동일 요청·다른 입력 | 요청 ID뿐 아니라 입력 fingerprint·위치·선택 설정을 비교해 충돌 |
| LLM 실패 뒤 재실행 | 저장된 실행 스냅샷을 재사용. 원문·관계를 새로 조회해 바꾸지 않음 |
| 결과 저장 뒤 checkpoint 또는 발행 실패 | 저장 결과를 찾아 idempotent 저장으로 참조를 복구하고 재발행. LLM 재호출 없음 |
| 발행 후 응답 유실 | 같은 작업 ID의 완료가 중복 전달될 수 있음. 수신자 중복 처리가 필요 |
| LLM 응답 뒤 결과 저장 실패 | 결과가 남지 않아 재호출할 수 있음. 모델 호출 exactly-once는 보장하지 않음 |
| 기존 스냅샷·결과 참조의 객체 유실 | 새로운 자료로 조용히 재생성하지 않고 명시적으로 실패 |
| 오류 처리 중 작업 상태 저장도 실패 | 원래 오류를 유지하고 부가 오류를 기록. 실행권이 남아 별도 lease 복구가 필요 |

fake를 새 서비스에 연결하는 테스트는 메모리 상태를 이용한 재개 시뮬레이션이다.
실제 프로세스 장애·DB 트랜잭션·분산 동시성·S3 보존·Kafka offset을 검증한 것은 아니다.
운영에서는 lease 만료 후의 실행권 회수, 오래된 실행자의 쓰기 차단, 저장소 간 부분 성공을 별도로 설계한다.

## 다음 마이그레이션 경계

1. 내부 판단 함수별 실제 정책과 단위 테스트를 구현한다. 청킹·추출 프롬프트·근거 구성은 기존 AI에서 선별한다.
2. S3 `input.json`·실행 스냅샷·`result.json`의 스키마·키·권한·만료 계약을 맞춘다. 기본 입력은 갱신하지 않는다.
3. Content 추가 조회의 인증·범위·본문·속성·revision·누락/삭제 응답을 확정한다.
4. 그래프 반영 기준과 제한된 관계 탐색, 대기 예산을 확정한다. 본문 revision만으로 모든 관계 변경의 반영을 판단하지 않는다.
5. 실제 LLM 품질 평가와 어댑터별 통합 테스트를 수행한다. fake 테스트 통과를 운영 연동 완료로 기록하지 않는다.

현재 제품용 HTTP·Kafka 계약은 추가하지 않았다. 내부 `PROPOSED`·`NO_CHANGE`·`FAILED`와
외부 완료 이벤트의 `SUCCEEDED`·`FAILED` 매핑, 중복 키·offset 처리·재시도 예산은 전달 어댑터에서 확정할 사항이다.
Content가 수행할 사용자 확정과 기준 revision 충돌 검사는 이 골격에서 실행하지 않는다.

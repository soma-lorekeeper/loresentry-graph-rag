# 갱신안 입력·결과 계약

> **상태:** MVP 구현 기준. 이 문서는 변경 문서와 관계를 읽어 S3에 제안만 저장하는 책임을 확정한다. 실제 JSON Schema, Content와의 직렬화 매핑 및 어댑터 구현 완료를 뜻하지 않는다.

## 책임과 종료 지점

Content가 변경 문서 전체의 본문·revision_no·현재 관계를 S3 `input.json`에 저장하고 Kafka로 요청 식별자와 객체 위치를 전달한다. Kafka가 S3 객체를 작성하는 것은 아니다.
GraphRAG는 입력과 필요한 추가 자료를 읽고, 문서 내용 변경과 새로운 관계를 제안한다. 검증된 제안은 S3 `result.json`에만 저장하며, 결과 위치·처리 상태를 Kafka로 발행하면 생성 요청의 처리가 종료된다.

GraphRAG는 이 과정에서 Content 문서나 확정 관계, Neptune의 확정 그래프를 수정하지 않는다. 완료 이벤트 수신도 제안의 자동 적용을 뜻하지 않는다. 사용자가 제안을 확정하면 Content가 원본에 반영하고, 확정 변경 이벤트를 통한 그래프 동기화는 별도 흐름으로 처리한다.

## 입력 범위와 크기

- 한 요청에는 최신화 대상인 변경 문서 전체를 포함한다. 프로젝트의 모든 문서를 의미하지 않으며, 변경 목록에서 일부만 조용히 골라 보내지 않는다.
- 첫 MVP는 변경 목록 최대 20개, ACTIVE 문서 본문당 최대 5,000자를 지원한다. 본문 기준 최대 100,000자이며 JSON 전체 바이트·토큰 한도와는 다르다.
- 문자 수는 전송된 원문 문자열의 Unicode 코드 포인트 수로 센다. Python `len(body_text)` 기준이며 UTF-8 바이트 수나 Java 문자열의 UTF-16 길이와 구분한다. 정규화·공백 제거 전에 검사한다.
- 초과 입력은 명시적 입력 실패로 처리한다. 일부 문서 누락, 원문 절단, 자동 분할 요청으로 성공 처리하지 않는다.
- TRASHED·DELETED 항목은 변경 목록에서 보존하지만 본문 생성 자료나 갱신 대상으로 사용하지 않는다. ACTIVE 문서의 필수 본문 누락이나 요청/S3 간 식별·revision_no 불일치는 입력 실패다.
- 추가 조회한 기존 설정·참고 문서는 변경 목록 20개와 구분한다. 별도의 조회 수·문맥 예산을 설정해야 하며 무제한 확장을 허용하지 않는다. 정확한 예산은 rules 구현의 계약 작업에서 고정한다.

## 입력과 추가 자료의 의미

| 자료 | 필요한 내용 | 공급 경계 |
|---|---|---|
| 요청 식별 | request_id, project_id, 입력 객체 위치 | Kafka 요청 |
| 변경 문서 | 문서 ID, 상태, 문서 revision_no, ACTIVE 본문, 현재 명시적 관계 | Content의 S3 입력 |
| 기존 설정 문서 | 대상 ID, 기준 revision_no, 현재 본문과 필요한 메타데이터 | 기본 입력 또는 Content 추가 조회 |
| 관련 관계 | 프로젝트 범위, 문서 ID·대상 문서 ID, 대상 분류별 relation_key, 관계 설명과 반영 상태 | 기본 입력 및 그래프 조회 |
| 실행 스냅샷 | 기본·추가 문서 원문과 revision_no, 관계, 선택 설정 | GraphRAG가 작업별로 별도 보관 |

변경 문서와 갱신 대상 문서는 동일한 개념이 아니다. 여러 변경 문서가 여러 기존 설정 문서의 제안에 영향을 줄 수 있다. 대상은 입력과 명시적 관계로 식별하고 이름 유사성만으로 문서를 합치거나 임의의 ID를 생성하지 않는다.
관계 그래프에서는 관련 ID·관계를 조회하고, 부족한 본문은 Content API로 조회한다. 추가 자료를 얻기 위해 Kafka로 입력 객체 재작성을 요청하지 않는다.
기본 입력을 최신 조회 값으로 덮어쓰지 않고 추가 자료를 실행 스냅샷으로 보관한다. 저장된 실행 스냅샷은 재시도에서 재사용한다.

## S3 결과의 논리 구조

아래 이름은 구현할 결과 JSON의 기준안이다. 기존 내부 dataclass나 이미 배포된 외부 스키마로 간주하지 않는다. 실제 연결 전에 Content 소비자와 JSON Schema로 고정한다.

| 항목 | 계약 |
|---|---|
| schema_version | 결과 스키마 버전 |
| request_id, project_id | 입력 요청과 같은 식별자 |
| outcome | PROPOSED, NO_CHANGE, FAILED |
| document_proposals | 기존 문서 내용 변경 제안 목록 |
| relation_proposals | 새로운 관계 추가 제안 목록 |
| sources | 사용한 문서 ID·revision_no와 출처. 추가 조회 문서도 포함 |
| evidence | 원본 문서 ID·revision_no·구간·인용문으로 식별하는 근거 목록 |
| error | FAILED의 코드·메시지. 정상 결과는 null |
| execution | 프롬프트·모델 버전, 호출 사용량과 평가 재현에 필요한 설정 |

### 문서 내용 변경 제안

대상 문서 ID, 기준 revision_no, 제안 필드, 제안 값과 근거 참조를 담는다. 첫 구현의 본문 텍스트(`body_text`) 교체 제안은 여러 기존 설정 문서를 지원한다. 단일 대상 제한을 두지 않는다.
새 문서 생성은 이 계약에 포함하지 않는다. 본문 외 속성까지 지원할 경우 허용 필드와 값 타입을 명시적으로 추가해야 하며 임의 필드 쓰기를 허용하지 않는다.
원문은 변경하지 않고 기존 값과 제안 값의 비교·확정을 Content가 수행한다. body_text는 분석용 텍스트이고 Content의 저장 필드 body는 에디터 JSON이다. 확정 시 JSON으로 반영하는 변환 계약은 실제 연동 전에 정의하며 문자열 후보를 body JSON으로 곧바로 쓰지 않는다.

### 새로운 관계 제안

제안 작업 ADD, 양 끝 문서 ID·분류, 방향별 relation_key, 관계 설명, 양 끝 문서의 기준 revision_no와 근거 참조를 담는다. 실제 relation_id를 생성하거나 관계를 저장하는 명령이 아니다.
Content 관계는 업무상 무방향 연결이고 저장 시에는 양방향 행과 대상 분류별 키로 표현한다. 신규 연결 제안의 중복은 양 끝 ID를 정렬한 문서 쌍으로 판별하며 방향별 relation_key를 별개의 의미 관계로 세지 않는다. 이미 존재하는 같은 관계는 신규 제안으로 중복 반환하지 않는다.
양 끝 문서는 같은 프로젝트의 확인된 ACTIVE 문서여야 한다. 대상 분류와 맞지 않는 관계 키, 없는 문서, 자기 자신과의 관계는 검증 실패로 처리한다.
기존 관계 삭제·변경 제안은 이번 신규 관계 추가 범위에 자동 포함하지 않는다.
문서 revision_no만으로 관계 상태 변경까지 검출할 수 없다. Content 확정 시 관계의 현재 존재 여부·허용 조건을 다시 검사해야 하며, 관계 변경 버전의 외부 필드는 연동 전에 합의한다.

### 근거와 결과 검증

근거 위치는 원본 본문 문자열의 코드 포인트 인덱스 `[start:end]`이며 시작 포함·끝 제외다. quote는 해당 revision_no 원문의 구간과 정확히 같아야 한다. 전처리하거나 청킹해도 원문 위치를 보존한다.
문서 제안과 관계 제안 모두 근거를 요구한다. 인용문 일치는 출처의 존재를 검증할 뿐, 제안이 의미적으로 정당한지는 실제 LLM 품질 평가에서 별도로 검증한다.
전체 문서 제안과 관계 제안이 모두 없을 때만 NO_CHANGE다. 관계 제안만 있어도 PROPOSED다.
여러 후보 중 검증 실패가 하나라도 있으면 MVP에서는 요청 전체를 FAILED로 처리하고 두 제안 목록을 비운다. 일부 후보를 버리고 NO_CHANGE로 위장하지 않는다. 이미 유효한 결과로 저장된 요청은 재생성하지 않는다.

## 생성과 전달

최대 입력을 무조건 한 번의 모델 호출에 넣지 않는다. 대상별로 필요한 변경 원고·기존 설정·근거를 묶고, 같은 대상에 대한 여러 입력의 영향을 함께 검토하여 후보를 통합한다. 관계 후보도 요청 전체에서 중복·충돌을 검증한다.
여러 호출이 필요한 경우 호출 예산·부분 호출 실패·사용량 합산을 서비스와 모델 어댑터에서 처리한다. rules는 자료 선택, 청킹, 문맥·프롬프트 구성과 후보 검증을 담당하며 IO 포트를 직접 호출하지 않는다.

| S3 결과 | Kafka GraphRefreshCompleted |
|---|---|
| PROPOSED | SUCCEEDED와 result 위치. 적용 완료를 뜻하지 않음 |
| NO_CHANGE | SUCCEEDED와 result 위치. S3의 빈 제안 목록으로 구분 |
| FAILED | FAILED와 error. 실패 결과를 S3에 저장했다면 result 위치도 전달 |

완료 이벤트에는 문서 본문·제안 내용·관계 목록을 복제하지 않는다. 식별자와 결과 위치·상태·실패 요약 등 전달 메타데이터만 담는다. 이벤트 외형은 [메시지 계약](../reference/message-contract.md)을 따른다.
S3 결과 저장 후 발행한다. 결과 저장이 실패하면 존재하지 않는 위치를 성공으로 알리지 않고 복구·재시도한다. 재시도 소진 시의 전달 계층 실패는 result=null과 error로 알릴 수 있으며, 이는 정상적인 제안 결과 저장 완료와 구분한다.
발행 뒤 응답 유실·완료 상태 기록 실패는 중복 발행을 만들 수 있다. Content는 요청 식별자로 중복 처리하고, 결과 저장 후 발행 실패에서는 저장된 결과로 재발행한다.

## 현재 코드와의 차이 및 구현 완료 기준

현재 `app/refresh/models.py`의 DocumentProposal은 문서 필드 후보만 표현하며 별도의 관계 제안 값이 없다. SelectionSettings의 기본 10개·10,000자도 이번 변경 입력 20개·문서당 5,000자 계약을 구현한 값이 아니다.
현재 서비스는 한 번의 모델 호출 골격이고 RefreshRules는 미구현이다. 따라서 문서 수정만으로 다중 대상 생성·관계 제안·새 한도가 구현되었다고 보고하지 않는다.

후속 rules 마이그레이션에서는 입력 한도와 참고 자료 예산을 분리하고, 문서·관계 후보 모델, 다중 대상 문맥과 후보 통합, 결과 직렬화·완료 상태 매핑을 구현한다. 실제 어댑터를 연결하기 전 S3 상세 스키마·접근 권한·만료와 관계 반영 기준을 합의한다.
고정 사례에는 다중 입력·다중 대상, 관계만 제안, 문서와 관계 동시 제안, 변경 없음, 입력 초과, 양 끝 순서가 다른 중복 관계, 허위 근거, 일부 후보 실패를 포함한다. 원본 문서·확정 그래프에 쓰기가 없고 S3 결과 저장 후 완료를 발행하는지도 검증한다.

## rules v1 실행 예산

변경 입력은 20개, ACTIVE 본문은 원문 5,000자까지다. 추가 문서는 별도로
최대 20개이며 명시적 관계를 깊이 1까지 탐색한다. 변경 문서 수에는 비활성 항목도
포함한다. 문맥은 JSON 출처 마커와 프롬프트를 포함해 호출당 240,000 코드 포인트,
모델 호출은 요청당 최대 20회로 제한한다. 초과는 잘라내지 않고 실패한다.
본문 조각은 1,000자 이하로 분할한다. 이는 토큰 보장치가 아니므로 실제 모델
어댑터에서는 모델별 토큰 한도를 추가 검증해야 한다.

문자열 설정값과 버전은 요청·실행 스냅샷으로 고정한다. 기본 모델 이름
`unconfigured`는 실제 모델 선택이 필요함을 뜻한다. 이 단계는 fake로 검증한다.

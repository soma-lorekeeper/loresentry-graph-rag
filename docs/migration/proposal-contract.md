# 갱신안 입력·결과 계약

> **상태:** MVP 구현 기준. 이 문서는 변경 문서와 관계를 읽어 S3에 제안만 저장하는 책임을 확정한다. 내부 엄격 입력 스키마와 S3 어댑터는 구현했으며 [저장소 계약](../implementation/S3_ARTIFACTS.md)을 따른다. Content와의 직렬화 매핑·Kafka 연결 완료를 뜻하지 않는다.

## 책임과 종료 지점

Content가 변경 문서 전체의 본문·revision_no·현재 관계를 S3 `input.json`에 저장하고 Kafka로 요청 식별자와 객체 위치를 전달한다. Kafka가 S3 객체를 작성하는 것은 아니다.
GraphRAG는 입력과 필요한 추가 자료를 읽고, 문서 내용 변경과 새로운 관계를 제안한다. 검증된 제안은 S3 `result.json`에만 저장하며, 결과 위치·처리 상태를 Kafka로 발행하면 생성 요청의 처리가 종료된다.

GraphRAG는 이 과정에서 Content 문서나 확정 관계, Neptune의 확정 그래프를 수정하지 않는다. 완료 이벤트 수신도 제안의 자동 적용을 뜻하지 않는다. 사용자가 제안을 확정하면 Content가 원본에 반영하고, 확정 변경 이벤트를 통한 그래프 동기화는 별도 흐름으로 처리한다.

## 입력 범위와 크기

- 한 요청에는 최신화 대상인 변경 문서 전체를 포함한다. 프로젝트의 모든 문서를 의미하지 않으며, 변경 목록에서 일부만 조용히 골라 보내지 않는다.
- 첫 MVP는 변경 목록 최대 20개, ACTIVE 문서 본문당 최대 5,000자를 지원한다. 본문 기준 최대 100,000자이며 JSON 전체 바이트·토큰 한도와는 다르다.
- 문자 수는 전송된 원문 문자열의 Unicode 코드 포인트 수로 센다. Python `len(body_text)` 기준이며 UTF-8 바이트 수나 Java 문자열의 UTF-16 길이와 구분한다. 정규화·공백 제거 전에 검사한다.
- 초과 입력은 명시적 입력 실패로 처리한다. 일부 문서 누락, 원문 절단, 자동 분할 요청으로 성공 처리하지 않는다.
- TRASHED·DELETED 항목은 변경 목록에서 보존하지만 본문 생성 자료나 갱신 대상으로 사용하지 않는다. ACTIVE 문서의 필수 본문 누락이나 요청/S3 간 식별·revision_no 불일치는 입력 실패다.
- 추가 조회한 기존 설정·참고 문서는 변경 목록 20개와 구분한다. 별도의 조회 수·문맥 예산을 설정해야 하며 무제한 확장을 허용하지 않는다. 예산은 아래 rules v1 실행 예산을 따른다.

## 입력과 추가 자료의 의미

| 자료 | 필요한 내용 | 공급 경계 |
|---|---|---|
| 요청 식별 | request_id, project_id, 입력 객체 위치 | Kafka 요청 |
| 변경 문서 | 문서 ID, 상태, 문서 revision_no, ACTIVE 본문, 현재 명시적 관계 | Content의 S3 입력 |
| 기존 설정 문서 | 대상 ID, 기준 revision_no, 현재 본문과 필요한 메타데이터 | 기본 입력 또는 Content 추가 조회 |
| 관련 관계 | 프로젝트 범위, 문서 ID·대상 문서 ID, 대상 분류별 relation_key, 관계 설명과 반영 상태 | 기본 입력 및 그래프 조회 |
| 실행 스냅샷 | 기본·추가 문서 원문과 revision_no, 관계, 선택 설정 | GraphRAG가 작업별로 별도 보관 |

변경 문서와 갱신 대상 문서는 동일한 개념이 아니다. 여러 변경 문서가 여러 기존 설정 문서의 제안에 영향을 줄 수 있다. 대상은 입력과 명시적 관계로 식별하고 이름 유사성만으로 문서를 합치거나 임의의 ID를 생성하지 않는다.
관계 그래프에서는 관련 ID·관계를 조회하고, 부족한 본문은 Content API로 조회한다. 추가 자료를 얻기 위해 Kafka로 입력 객체 재작성을 요청하지 않는다.
기본 입력을 최신 조회 값으로 덮어쓰지 않고 추가 자료를 실행 스냅샷으로 보관한다. 저장된 실행 스냅샷은 재시도에서 재사용한다.

## S3 결과의 논리 구조

아래 이름은 구현할 결과 JSON의 기준안이다. 기존 내부 dataclass나 이미 배포된 외부 스키마로 간주하지 않는다. 실제 연결 전에 Content 소비자와 JSON Schema로 고정한다.

| 항목 | 계약 |
|---|---|
| schema_version | 결과 스키마 버전 |
| request_id, project_id | 입력 요청과 같은 식별자 |
| outcome | PROPOSED, NO_CHANGE, FAILED |
| document_proposals | 기존 문서 내용 변경 제안 목록 |
| new_document_proposals | 원고에서 발견한 새 설정 문서 생성 제안 목록 |
| relation_proposals | 새로운 관계 추가 제안 목록 |
| facts | 생성에 사용한 역할·행위·시점·확실성·범위와 원문 근거를 갖춘 개별 사실 |
| sources | 사용한 문서 ID·revision_no와 출처. 추가 조회 문서도 포함 |
| evidence | 원본 문서 ID·revision_no·구간·인용문으로 식별하는 근거 목록 |
| error | FAILED의 코드·메시지. 정상 결과는 null |
| execution | 프롬프트·모델 버전, 호출 사용량과 평가 재현에 필요한 설정 |

### 문서 내용 변경 제안

대상 문서 ID, 기준 revision_no, 제안 필드, 제안 값과 근거 참조를 담는다. 첫 구현의 본문 텍스트(`body_text`) 교체 제안은 여러 기존 설정 문서를 지원한다. 단일 대상 제한을 두지 않는다.
원고(`MANUSCRIPT`)는 읽기 전용이며 본문 수정 제안은 거절한다. 평가에서는 최초 입력과 저장된 원고의 본문·메타데이터가 동일한지 검사한다. 본문 외 속성까지 지원할 경우 허용 필드와 값 타입을 명시적으로 추가해야 하며 임의 필드 쓰기를 허용하지 않는다.
원문은 변경하지 않고 기존 값과 제안 값의 비교·확정을 Content가 수행한다. body_text는 분석용 텍스트이고 Content의 저장 필드 body는 에디터 JSON이다. 확정 시 JSON으로 반영하는 변환 계약은 실제 연동 전에 정의하며 문자열 후보를 body JSON으로 곧바로 쓰지 않는다.

### 새 설정 문서 생성 제안

`new_document_proposals`는 candidate_id, folder_code, name, body_text와 근거를 담는다.
설정 분류는 CHARACTER, WORLDVIEW, LOCATION, ORGANIZATION, ITEM, EVENT이며
MANUSCRIPT 생성은 금지한다. 임시 ID는 `new:{folder_code}:{name}` 형식으로 고정한다.
원고 한 편만 있고 기존 설정 문서가 없어도 생성 후보와 원고 연결을 제안할 수 있다.
새 후보끼리 또는 기존 설정과 연결할 수도 있으며 실제 문서·그래프는 여기서 생성하지 않는다.

후보에는 변경된 원고의 정확한 인용 근거가 필요하다. 이름은 200자, 본문은 요청의
본문 한도(기본 5,000자), 생성 후보는 요청당 20개까지다. 첫 모델 호출이 전체 원고를
검토하여 생성 후보와 그 연결을 담당하고 후속 호출은 기존 설정 수정·기존 문서 연결만
제안한다. 같은 후보의 중복은 근거를 합치고 본문이 다르면 요청 전체를 실패 처리한다.
조회된 동일 프로젝트의 ACTIVE 설정에서 독립 필드 `title`, 속성 `name`·`title`·`alias`와
동일 분류·이름인 후보는 거절한다. `alias`는 한 문자열 값만 사용하며 구분자나 배열을
추정하지 않는다. 이름의 공백·Unicode·대소문자 정규화는 중복 검사에만 쓰며 원고 본문은
정규화하지 않는다. 본문의 단순 언급은 해당 설정의 독립 문서가 있다는 뜻이 아니다.
동명이인이나 별칭의 의미적 동일성은 모델과 승인자의 검토 대상이다.
현재 조회는 명시적 관계 범위이므로 프로젝트 전체의 미조회 설정과 중복되지 않는다는
보장은 없다. 운영 연동 시 Content에서 전체 설정 중복과 현재 권한을 다시 확인해야 한다.

Content는 승인한 생성 후보에 실제 문서 ID를 발급하고 candidate_id 매핑으로 관계를
확정해야 한다. 이 승인·생성·연결 API는 아직 미연결이다. `body_text`를 에디터 body JSON으로
변환하는 계약도 기존 수정 제안과 동일하게 후속 연동 대상이다.

### 새로운 관계 제안

제안 작업 ADD, 양 끝 문서 ID·분류, 방향별 relation_key, 관계 설명, 양 끝 문서의 기준 revision_no와 근거 참조를 담는다. 실제 relation_id를 생성하거나 관계를 저장하는 명령이 아니다.
Content 관계는 업무상 무방향 연결이며 V10 이후 문서쌍당 한 행을 저장한다.
조회 응답은 현재 문서에서 바라본 상대 분류의 키를 계산한다. GraphRAG 제안은 두 방향의
분류 키를 검증하지만 Content의 저장 행 두 개를 뜻하지 않는다. 신규 연결 제안의 중복은
양 끝 ID를 정렬한 문서쌍으로 판별한다. 이미 존재하는 같은 관계는 중복 반환하지 않는다.
양 끝은 같은 프로젝트의 확인된 ACTIVE 문서 또는 같은 결과의 생성 후보여야 한다. 기존 문서는 문서 ID와 실제 revision_no, 생성 후보는 candidate_id와 null revision으로 참조한다. 대상 분류와 맞지 않는 관계 키, 없는 문서·후보, 자기 자신과의 관계는 검증 실패로 처리한다.
기존 관계 삭제·변경 제안은 이번 신규 관계 추가 범위에 자동 포함하지 않는다.
문서 revision_no만으로 관계 상태 변경까지 검출할 수 없다. Content 확정 시 관계의 현재 존재 여부·허용 조건을 다시 검사해야 하며, 관계 변경 버전의 외부 필드는 연동 전에 합의한다.

### 근거와 결과 검증

근거 위치는 원본 본문 문자열의 코드 포인트 인덱스 `[start:end]`이며 시작 포함·끝 제외다. quote는 해당 revision_no 원문의 구간과 정확히 같아야 한다. 전처리하거나 청킹해도 원문 위치를 보존한다.
수정·생성·관계 제안 모두 근거를 요구한다. 인용문 일치는 출처의 존재를 검증할 뿐, 제안이 의미적으로 정당한지는 실제 LLM 품질 평가에서 별도로 검증한다.
현재 모델 생성 계약 `refresh-candidate-v5`에서 기존 수정·신규 설정의 근거는
`{"marker":"C0001"}`로 반환한다. 모든 제안은 비어 있지 않은 `fact_ids`로
같은 응답의 `facts`를 참조한다. 개별 사실에는 행위자·수령인·대상, 원문의 행위 표현,
확실성·일부/전체·시점, 짧은 사실 문장과 `source:{marker}`가 있다.
한 사실은 한 마커를 선택하고 서버가 해당 마커의 전체 원문 quote와 정확한 위치를 복원한다.
모델이 발췌·인용문·숫자 위치를 덧붙이거나 원문을 합성·재작성하지 않는다.
역할의 표면 표현과 행위는 선택한 마커의 quote에 실제로 포함되어야 한다.
사실 근거 크기는 요청의 `chunk_chars`(기본 1,000자) 한도다. statement는 원문의 역할·
부정·조건·범위를 보존해 500자까지 요약할 수 있고 action·surface는 각각 200자까지다.
`chunk_overlap_chars`는 기본 0이며 양수이면 앞 구간의 완전한 문장을 다음 구간에
겹쳐 담는다. 값은 `chunk_chars`보다 작아야 하고, 다음 새 문장과 함께 한도 안에
들어가는 문장만 겹친다. 원문 위치·전체 구간 크기 한도·단일 마커 계약은 그대로다.
기본 0은 과거 청킹과 저장 바이트를 유지하며, 겹침 때문에 원문에 없는 인물 정체를
문서 참조로 추정하는 예외를 허용하지 않는다.
행위자·수령인의 문서 참조는 명시 제목·이름·별칭 또는 이번 후보 이름과 일치할 때만
허용한다. 익명 담당자·어머니·대명사는 원문 표현을 보존하고 문서 참조를 비운다.
이름으로 참조할 때는 해당 이름과 행동을 함께 담은 마커를 선택하며 원문이 별칭이면
surface도 그 별칭을 유지한다. 승인 대상 사건·행동은 object로 유지하고 직접 승인받은
사람이 명시되지 않으면 recipient는 null로 둔다. 승인자·운반자·수령인을 서로 대신하지 않는다.
관계 wire에는 별도 description·evidence를 허용하지 않으며 서버가 참조 사실의
statement와 근거를 조합한다. 문서 본문은 자유롭게 생성하므로 사실 참조 일치만으로
전체 본문의 의미 정확성을 보증하지 않는다. 원문의 역할·불확실성 해석도 별도 평가 대상이다.
사실은 호출당 최대 100개이며 요청 집계는 호출 예산에 비례한 상한을 적용한다.
로컬 fact ID는 내용을 포함한 해시로 정규화하고 서로 다른 호출의 같은 ID를 혼동하지 않는다.
알 수 없는 참조와 역할의 명시 식별 불일치는 전체 후보 실패다. 유효하지만 제안에
쓰이지 않은 중간 사실은 검증 후 최종 결과에서 제외한다.
어댑터가 같은 호출의 문맥에서 마커를 찾아 위의 ID·revision·정확한 구간·인용문으로
복원한다. 없는 마커나 모델이 추가한 위치·인용문은 거절한다. 최종 결과의 근거 형식과
원문 대조 검증은 유지한다. 과거 v1/v2 전체 구간, v3 마커 후보와 v4/p8·p9·p10의
`source:{marker,excerpt}` 후보는 저장 자료 읽기에만 사용한다. v4 사실 발췌는 원문에서
유일하게 일치하는 500자 이하 구간으로 복원하며 현행 live 계약을 완화하지 않는다.
기존 문서 수정·새 설정 생성·관계 추가 제안이 모두 없을 때만 NO_CHANGE다. 어느 한 종류만 있어도 PROPOSED다.
현행 v5 후보에 구체적 검증 진단이 있으면 같은 호출 범위에서 최대 한 번 보완한다.
새 후보는 기존 검증을 모두 거쳐 원 후보를 통째로 교체하며, 이전에 통과한 다른 호출은
재생성하지 않는다. 보완 후에도 검증 실패가 남거나 전체 통합에서 충돌하면 요청 전체를
FAILED로 처리하고 세 제안 목록을 비운다. 일부 후보를 버리고 NO_CHANGE로 위장하지 않는다.
타입 후보의 보완 입력에서는 내부 해시 ID를 짧은 로컬 ID로 바꾸고 모든 사실 참조·
진단을 함께 매핑한다. 미선언 참조와 충돌하는 ID는 사용하지 않으며 저장 결과는 기존
내용 기반 해시를 유지한다. ID 변환으로 사실·본문·출처를 수정하지 않는다.
이미 저장된 결과는 FAILED를 포함해 재생성하지 않는다. 새 생성 평가는 새 요청 ID로 실행한다.

결과 v3의 선택적 `execution.attempts`에는 최초·보완 시도별 호출 범위, 후보 수, 검증 결과,
실패 코드·내부 진단과 관측 사용량을 보존한다. 파싱 실패로 후보 수를 알 수 없으면
0 대신 null로 기록한다. 이력이 없는 과거 결과도 읽으며, 이력이 있는 결과는 시도 순서와
사용량 합계·최종 상태를 검사한다. 통합 실패의 진단은 선택적
`execution.validation_diagnostics`로 보존한다. 내부 진단·출처를 Markdown 리포트에 노출하지 않는다.

## 생성과 전달

기본 `separate_discovery=False`에서는 설정 대상별로 한 번씩 호출하며 첫 호출만 새 설정을
생성한다. `True`에서는 기존 설정을 수정할 수 없는 신규 탐색 1회 뒤 대상별 수정 N회를
호출한다. 활성 변경은 있지만 대상이 없으면 두 정책 모두 한 번 호출한다. 각 호출에는 선택된
모든 ACTIVE 문서·근거를 함께 제공한다. 입력·문맥·호출 한도를 넘으면 분할·절단하지 않고
실패한다. 각 후보는 요청 전체에서 통합 검증하며 관계도 중복·충돌을 다시 검증한다.
기존 관계쌍은 실행 대상 순서에서 먼저 등장하는 endpoint의 호출이 담당한다.
양 끝에 실행 대상이 없거나 신규 후보가 있으면 첫 호출이 담당한다. 방향을 바꿔도
같은 호출 소유이며 다른 호출의 관계 반환은 `INVALID_RELATION_SCOPE`다.
입력에 허용된 기존 문서쌍 목록을 제공한다. 한 관계 원소가 두 방향의 키를 함께 표현하므로
반대 방향 원소를 따로 반환하지 않는다.
전체 집계는 소유권으로 나뉜 후보를 합쳐 원문·중복·충돌을 다시 검증한다.
서로 다른 설명을 임의로 골라 합치거나 비소유 관계를 버리고 성공 처리하지 않는다.
여러 호출이 필요한 경우 호출 예산·부분 호출 실패·사용량 합산을 서비스와 모델 어댑터에서 처리한다.
`max_model_calls`는 보완을 포함한 실제 시도 한도다. 보완 전에 남은 최초 호출을 예약하고
추가 문맥도 문자·어댑터 토큰 예산 안에 있어야 한다. 파싱·검증에서 폐기된 응답의 관측
토큰도 합산한다. SDK·연동 오류 재시도와 검증 피드백 보완은 별개이며 SDK 자체 재시도는
사용하지 않는다. rules는 자료 선택, 청킹, 문맥·프롬프트 구성과 후보 검증을 담당하며 IO 포트를 직접 호출하지 않는다.

| S3 결과 | Kafka GraphRefreshCompleted |
|---|---|
| PROPOSED | SUCCEEDED와 result 위치. 적용 완료를 뜻하지 않음 |
| NO_CHANGE | SUCCEEDED와 result 위치. S3의 빈 제안 목록으로 구분 |
| FAILED | FAILED와 error. 실패 결과를 S3에 저장했다면 result 위치도 전달 |

완료 이벤트에는 문서 본문·제안 내용·관계 목록을 복제하지 않는다. 식별자와 결과 위치·상태·실패 요약 등 전달 메타데이터만 담는다. 이벤트 외형은 [메시지 계약](../reference/message-contract.md)을 따른다.
S3 결과 저장 후 발행한다. 결과 저장이 실패하면 존재하지 않는 위치를 성공으로 알리지 않고 복구·재시도한다. 재시도 소진 시의 전달 계층 실패는 result=null과 error로 알릴 수 있으며, 이는 정상적인 제안 결과 저장 완료와 구분한다.
발행 뒤 응답 유실·완료 상태 기록 실패는 중복 발행을 만들 수 있다. Content는 요청 식별자로 중복 처리하고, 결과 저장 후 발행 실패에서는 저장된 결과로 재발행한다.

## 현재 코드와의 차이 및 구현 완료 기준

현재 내부 모델·rules·다중 호출 조율과 결과 JSON 변환·완료 상태 매핑을 구현했다.
구체적인 이식 위치와 검증 범위는 [rules 이식 결과](rules-implementation.md)를 따른다.
실제 어댑터를 연결하기 전 입력·결과 JSON Schema, 접근 권한·만료와 관계 반영 기준을 합의한다.

## rules v1 실행 예산

변경 입력은 20개, ACTIVE 본문은 원문 5,000자까지다. 추가 문서는 별도로
최대 20개이며 명시적 관계를 깊이 1까지 탐색한다. 변경 문서 수에는 비활성 항목도
포함한다. 문맥은 JSON 출처 마커와 프롬프트를 포함해 호출당 240,000 코드 포인트,
모델 호출은 요청당 최대 20회로 제한한다. 초과는 잘라내지 않고 실패한다.
본문 조각은 1,000자 이하로 분할한다. 이는 토큰 보장치가 아니므로 실제 모델
어댑터에서는 모델별 토큰 한도를 추가 검증해야 한다.

문자열 설정값과 버전은 요청·실행 스냅샷으로 고정한다. 기본 모델 이름
`unconfigured`는 실제 모델 선택이 필요함을 뜻한다. 이 단계는 fake로 검증한다.

## 실행 가능한 결과 변환과 예시

[serialization.py](../../app/refresh/serialization.py)의 `result_to_payload`는
`refresh-result-v3` 결과를 JSON에 넣을 수 있는 값으로 변환한다. 공통 근거는
최상위 `evidence`에 한 번 저장하고 각 제안의 `evidence_refs`가 참조한다.
`facts`도 같은 근거 사전을 참조하고 제안은 `fact_ids`로 해당 사실을 연결한다.
`sources.origin`은 변경 입력 `INPUT`과 추가 조회 `CONTENT`를 구분한다.
`execution`에는 모델·프롬프트·후보 스키마 버전, 선택 예산, 입력 fingerprint,
선택된 대상, 그래프 관측 버전, 이번 결과 생성 시도의 사용량을 기록한다.
`execution.schema_version`은 요청에 설정된 후보 계약이며,
`execution.candidate_schema_version`은 실제 후보를 검증한 계약이다. 과거 고정 후보를
사용하는 오프라인 평가와 저장 응답 재생에서는 두 값이 다를 수 있다. 현행 실제 호출은
v5 계약을 적용한다. v3 저장 결과의 v4/v5 후보는 비어 있지 않은 사실 참조를 요구하며,
사실·참조·실제 계약 메타데이터가 손상된 저장 결과는 거절한다. 과거 결과에 실제 계약
필드가 없으면 요청 계약을 기준으로 읽는다.
재시도에서 소모한 이전 시도의 토큰은 누적 과금 기록이 아니며 별도 관측이 필요하다.

고정 예시: [제안 있음](../examples/refresh/result-proposed.json),
[새 설정과 연결 제안](../examples/refresh/result-new-settings.json),
[변경 없음](../examples/refresh/result-no-change.json),
[실패](../examples/refresh/result-failed.json),
[완료 성공](../examples/refresh/completed-success.json),
[저장 불가 완료 실패](../examples/refresh/completed-storage-failed.json).
이 고정 결과는 과거 v3 후보 fixture를 현행 결과 저장 형식으로 변환한 예시다.
현행 v5의 구조화 사실과 제안 참조는 [독립 의미 평가 자료](../../evaluation/semantic_cases.py)와
[품질 검증 기록](refresh-quality.md#현행-구조화-사실-평가)에서 확인한다.
실제 소비자와 합의된 JSON Schema나 배포된 Kafka producer를 뜻하지 않는다.
`result_from_payload`는 v3와 과거 v1/v2 결과를 복원하며 출처·실행 메타데이터는
저장 JSON에 보존된다. 외부 응답 역직렬화와 S3 객체 무결성 검사는 실제 어댑터의 책임이다.

서비스는 저장 실패 시 완료를 발행하지 않고 오류를 전달한다. 전달 계층이 재시도를
소진한 뒤 `storage_failure_completion`으로 `result=null`인 실패 값을 만들 수 있다.
이 함수 자체는 발행하지 않으며, 재시도 소진 정책·Kafka 헤더·offset은 후속 구현이다.

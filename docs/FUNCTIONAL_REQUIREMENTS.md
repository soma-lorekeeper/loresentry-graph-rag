# GraphRAG 기능 요구사항 명세서

## 1. 목적과 적용 범위

GraphRAG가 제공해야 하는 동작과 수용 기준을 정의하고, 현재 구현 범위를 함께 표시한다.
기준은 2026-10-13 로컬 작업 디렉터리의 코드다. 커밋되지 않은 프롬프트 수정도 포함하며,
운영 배포·외부 서비스 연결이 완료됐다는 뜻은 아니다.

현재 범위는 서비스 진단과 내부 갱신안 생성이다. 갱신안은 기존 설정 본문 수정,
새 설정 문서 생성, 관계 추가를 제안하는 결과이며 원본에 적용하는 명령이 아니다.
Content가 원본 문서와 사용자 확정을 소유하고, 확정 변경의 그래프 동기화는 별도 기능이다.
문서·원고·설정·관계·revision의 의미는 [도메인 용어집](domain-glossary.md)을 따른다.

| 상태 | 의미 |
|---|---|
| 구현 | 명시한 범위의 코드가 존재한다. 내부 구현·로컬 검증을 운영 연결과 동일시하지 않는다. |
| 부분 구현 | 일부 경로만 구현됐거나 프롬프트 지시·평가에 의존하며 전체 기준 충족은 미확인이다. |
| 미구현 | 현재 실행 가능한 기능이 없다. 후속 요구사항으로 구분한다. |

수용 기준은 요구사항의 충족 판정 조건이며, 이 문서 작성 중 해당 시나리오를 모두 실행했다는 뜻은 아니다.
비기능 조건은 [비기능 요구사항 명세서](NON_FUNCTIONAL_REQUIREMENTS.md)에서 관리한다.

## 2. 현재 제공 인터페이스

HTTP 앱은 아래 진단 API만 제공한다. 갱신안 생성은 의존성을 주입한 내부 Python 서비스로
실행하며 HTTP·Kafka 요청 수신 경로에 연결하지 않았다.

| ID | 요구사항 | 수용 기준 | 현재 상태 |
|---|---|---|---|
| FR-001 | 서비스 식별 정보를 제공해야 한다. | `GET /`가 `200`과 `service=graph-rag-api`를 반환하고 외부 서비스를 호출하지 않는다. | 구현: HTTP |
| FR-002 | 프로세스 생존 상태를 외부 의존성 없이 제공해야 한다. | `GET /health`가 `200`과 `status=ok`를 반환한다. Neptune 장애를 이 API의 실패로 해석하지 않는다. | 구현: HTTP |
| FR-003 | Neptune 연결 진단을 제공해야 한다. | `GET /health/db`가 `/status`를 조회해 주소·역할·엔진·Gremlin 버전을 반환한다. 누락 메타데이터는 `unknown`, 통신·JSON·구조 오류는 `503`이다. 성공을 그래프 검색·쓰기 정상으로 해석하지 않는다. | 구현: 상태 조회만 |

상세 응답 형식과 예외 처리는 [제공 API](API.md), 외부 요청 구성은 [호출 API](API_CALLS.md)를 따른다.

## 3. 갱신안 입력과 자료 선택

| ID | 요구사항 | 수용 기준 | 현재 상태 |
|---|---|---|---|
| FR-004 | 요청과 변경 입력의 식별·문서 상태를 검증해야 한다. | 프로젝트·요청·fingerprint와 문서 ID·양수 revision·분류·상태가 유효해야 한다. 제공된 변경 manifest와 실제 입력이 다르거나 ID가 중복되면 실패한다. | 구현: 내부 rules, S3 입력 |
| FR-005 | 변경 입력을 보존하고 비활성 자료를 생성 범위에서 제외해야 한다. | TRASHED·DELETED도 변경 개수에 포함하되 분석 본문·수정 대상으로 사용하지 않는다. ACTIVE 본문 누락은 실패하며, 추가 조회로 최초 입력을 덮어쓰지 않는다. | 구현: 내부 rules |
| FR-006 | 명시 대상과 저장된 관계를 기준으로 관련 자료를 선택해야 한다. | 설정한 관계 키·깊이·문서 수 안에서 선택한다. 이름 유사성이나 무관한 조회 ID로 탐색을 확장하지 않는다. 명시 대상은 ACTIVE 설정이어야 하며, 대상 미지정 시 확보한 ACTIVE 설정을 대상으로 삼는다. | 구현: 선택 규칙. 실제 관계 조회는 미연결 |
| FR-007 | 필요한 추가 문서와 그래프 준비 상태를 확인해야 한다. | 필요한 문서의 누락·비활성 상태·다른 프로젝트 자료는 실패한다. 관련 그래프가 WAITING·UNKNOWN이면 `GRAPH_NOT_READY`로 처리하며 빈 READY 결과로 대체하지 않는다. | 구현: 내부 서비스·포트. 실제 Content·그래프 어댑터는 미구현 |
| FR-008 | 모델 호출 전에 실행 자료를 고정하고 출처가 있는 문맥을 구성해야 한다. | 입력·추가 문서·revision·선택 설정을 실행 스냅샷으로 저장한다. 문맥에 실제 이름·별칭, 변경 ID, 허용 대상·관계쌍, 원문 출처 마커를 전달한다. 재실행은 저장된 스냅샷을 재사용한다. | 구현: 내부 서비스, S3 어댑터 |

원문 보존·한도·청킹 조건은 비기능 명세서의 데이터 무결성과 자원 예산을 따른다.

## 4. 수정·생성·관계 제안

| ID | 요구사항 | 수용 기준 | 현재 상태 |
|---|---|---|---|
| FR-009 | 허용된 기존 설정의 본문 전체 교체안을 생성해야 한다. | 수정 허용 호출의 대상에만 `body_text`와 실제 기준 revision을 제안한다. 원고 수정·다른 필드·범위 밖 대상·잘못된 revision은 거절하고 기존과 같은 본문은 최종 수정 목록에서 제외한다. | 구현: 범위·필드·revision 검증 |
| FR-010 | 새 사실로 현재 설정을 수정하면서 나머지 내용은 보존해야 한다. | 새 원고와 충돌하는 현재 설명을 수정하고, 무관한 기존 사실을 유지한다. 과거 기록을 현재 상태로 바꾸거나 역할·부정·기간·일부/전체·확실성을 바꾸지 않는다. | 부분 구현: 프롬프트·등록 사례 평가. 자유 본문 전체의 의미 검증은 미완료 |
| FR-011 | 생성 허용 호출에서 여섯 유형의 독립 설정 후보를 제안해야 한다. | CHARACTER·WORLDVIEW·LOCATION·ORGANIZATION·ITEM·EVENT 기준으로 검토한다. 분류·이름·본문·변경 원고 근거·사실 참조와 정규형 candidate ID를 반환하고 실제 문서 ID는 발급하지 않는다. | 구현: 후보 계약·검증. 후보 발견의 완전성은 미확인 |
| FR-012 | 기존 설정 및 같은 요청의 중복 생성을 방지해야 한다. | 확보한 설정의 분류·이름·별칭에 대응하는 후보를 거절하고, 같은 후보의 충돌 본문도 실패한다. 본문에 단순히 언급된 이름을 독립 문서의 존재로 간주하지 않는다. | 부분 구현: 로드된 설정의 중복 검사. 프로젝트 전체 조회·동명이인 해소는 미구현 |
| FR-013 | 유효한 두 문서 또는 신규 후보 사이의 ADD 관계만 제안해야 한다. | 같은 프로젝트의 ACTIVE 기존 문서 또는 같은 결과의 신규 후보를 연결한다. 기존 끝에는 실제 revision, 후보 끝에는 null을 사용한다. 잘못된 분류 키·비소유 관계·자기 연결은 실패한다. 기존 연결은 제외하고 같은 쌍의 중복은 충돌 검사 후 정리한다. | 구현: 내부 검증·중복 정리 |
| FR-014 | 각 신규 설정을 해당 설정의 근거인 변경 원고와 연결해야 한다. | 후보끼리의 연결 외에 후보별 원고 ADD를 포함하고, 그 연결을 뒷받침하는 사실을 참조한다. | 부분 구현: 프롬프트·평가 사례. 모든 후보의 원고 연결을 강제하는 일반 검증은 없음 |
| FR-015 | 제안에 사용한 사실과 원문 근거를 추적할 수 있어야 한다. | 모든 제안이 알려진 비어 있지 않은 `fact_ids`를 참조한다. 사실별 한 출처 마커를 원본 구간으로 복원하고, action·surface의 원문 포함과 statement의 surface 보존을 검증한다. 행위자·수령인 문서 참조의 명시 이름·별칭 일치를 확인한다. | 구현: 구조·문자열·참조 검증. 의미적 역할 판별은 별도 |
| FR-016 | 관계 설명·근거는 참조 사실에서만 조립해야 한다. | 모델의 관계 응답에 별도 description·evidence를 받지 않는다. 서버가 참조 사실의 statement와 출처를 조합하고, 최종 결과에서 미사용 사실을 제거한다. | 구현: 모델 어댑터·rules |
| FR-017 | 모델 호출의 수정·생성·관계 소유권을 분리해야 한다. | 기본 모드는 대상별 호출 중 첫 호출만 신규 생성한다. `separate_discovery=true`이면 수정 금지 탐색 1회와 대상 수정 N회로 나눈다. 호출별 허용 기존 관계쌍과 신규 끝 관계 권한을 지킨다. | 구현: 내부 조율 |
| FR-018 | 구체적 후보 검증 오류만 제한적으로 보완하고 최종 결과를 일괄 검증해야 한다. | 현행 후보의 보완 가능한 진단에 대해 동일 호출 범위로 최대 1회 보완한다. 남은 최초 호출 예산을 예약하고 원 후보 전체를 교체한다. 성공한 다른 호출은 반복하지 않는다. 잔여 오류·통합 충돌은 전체 FAILED와 빈 제안 목록으로 처리한다. | 구현: 내부 서비스. 외부 장애 재시도와 구분 |

제안의 필드·분류 키·근거·버전 상세 계약은 [갱신안 입력·결과 계약](migration/proposal-contract.md)을 따른다.

## 5. 저장·복구·완료와 평가

| ID | 요구사항 | 수용 기준 | 현재 상태 |
|---|---|---|---|
| FR-019 | 결과를 업무 상태와 출처·실행 정보가 있는 JSON으로 저장해야 한다. | 제안이 하나라도 있으면 PROPOSED, 유효한 제안이 없으면 NO_CHANGE, 종료된 실패는 FAILED다. 요청 식별·세 제안 목록·facts·근거 사전·사용 자료·설정·사용량을 보존한다. 성공 결과 직렬화에는 실행 스냅샷이 필요하다. | 구현: 순수 변환, S3 어댑터 |
| FR-020 | S3 입력·스냅샷·결과를 요청 범위에서 읽고 불변 저장해야 한다. | 허용 입력 bucket/prefix와 바이트 fingerprint를 확인한다. 동일 요청·동일 내용은 재사용하고 다른 입력·설정·저장 내용은 충돌로 거절한다. 필수 객체 누락·손상·접근 실패를 미저장과 구분한다. | 구현: boto3 어댑터·로컬 HTTP 검증. 운영 버킷은 미검증 |
| FR-021 | 작업 소유권을 확인하고 저장된 복구 지점에서 재개해야 한다. | 다른 실행의 소유권을 해제하지 않는다. 저장된 결과는 FAILED도 재생성하지 않는다. 이미 완료된 요청은 다시 모델 호출·완료 발행하지 않는다. 저장된 복구 참조가 사라지면 최신 자료 조회로 대체하지 않고 실패한다. | 부분 구현: 조율·포트·fake 검증. 운영 job 저장소·임대 복구는 미구현 |
| FR-022 | 결과 저장 후 완료 값을 발행해야 한다. | 결과 위치·요청 식별·업무 결과·실패 정보를 전달하고 발행 후 완료 상태를 기록한다. 재시도 가능한 오류와 종료 실패를 구분하며, 발행 확인 유실 시 중복 완료를 허용하므로 수신자가 요청 기준으로 중복 처리한다. | 부분 구현: 값·직렬화·조율 구현. Kafka publisher·consumer는 미구현 |
| FR-023 | 평가에서 구조·누락·의미 검사와 검토 필요를 구분해야 한다. | 고정 후보 재생과 실제 모델 생성을 구분한다. 원고 보존·필수 제안·등록 사실/본문 기준을 점검하고 미등록 표현·자유 본문 의미는 검토 대상으로 남긴다. 결과 JSON·Markdown에 제안 차이·시도·사용량·지연을 기록한다. | 구현: 평가 도구. 운영 품질 합격을 의미하지 않음 |

현행 live 후보는 `refresh-candidate-v5`, 기본 프롬프트는 `refresh-prompt-v11`, 선택형은
`refresh-prompt-v12`, 결과는 `refresh-result-v3`다. 과거 후보 재생과 결과 읽기 호환을
현재 생성 계약 완화로 해석하지 않는다. 저장·외부 전달의 상세는
[S3 저장소](implementation/S3_ARTIFACTS.md), 평가 기준은 [검증 계획](implementation/TEST_PLAN.md)을 따른다.

완료 전송 값은 내부 PROPOSED·NO_CHANGE를 `SUCCEEDED`로, FAILED를 `FAILED`로 매핑한다.
`SUCCEEDED`는 제안 생성 처리 성공이며 사용자 승인·원본 적용·그래프 동기화 성공이 아니다.

다음은 기존 프로젝트 책임과 후속 계획에서 확인한 요구사항이다. 새 API 경로·검색 저장소·

| ID | 요구사항 | 수용 기준 | 현재 상태 |
|---|---|---|---|
| FR-024 | 운영 갱신 요청 수신·추가 자료 조회·완료 전달을 연결해야 한다. | 프로젝트 접근 권한, Content 입력 매핑, 실제 관계·문서 조회, 영속 job 소유권, Kafka 중복·재시작·실패 처리를 통합 검증한다. | 미구현: S3·모델 어댑터만 별도 구현 |
| FR-025 | Content의 확정 문서·명시적 관계를 그래프·색인에 동기화해야 한다. | 중복·역순 이벤트와 재시작 후 원본 상태로 수렴하고 휴지통·삭제 자료를 조회에서 제외한다. 미승인 제안을 확정 그래프에 저장하지 않는다. | 미구현: 그래프 모델·순서 계약 등 선행 결정 필요 |
| FR-026 | 접근 가능한 원문 검색과 명시적 관계 확장을 제공해야 한다. | 문서·revision·원문 위치로 추적 가능한 근거를 반환하고 다른 프로젝트·접근 불가·휴지통 자료를 제외한다. 검색 API·색인·품질 기준은 연동 전 확정한다. | 미구현: RAG/GraphRAG·임베딩·전문/벡터 검색 |
| FR-027 | AI Chat에 검색 근거를 제공해야 한다. | 합의한 검색 요청·오류·근거 계약으로 AI Chat이 호출한다. 대화 생성·도구 선택·스트리밍은 AI Chat 책임으로 유지한다. | 미구현 |

Content의 사용자 검토·실제 ID 발급·에디터 본문 변환·revision 재검사·후보 ID 치환은
GraphRAG 내부 생성 기능의 완료 조건이 아니라 외부 적용 단계의 연동 조건이다.
세부 순서와 선택적 기능은 [후속 계획](migration/follow-up.md)을 따른다.

## 7. 현재 상태의 확인 근거

HTTP 상태는 [앱 조립 코드](../app/main.py), 내부 실행·소유권·복구·보완 흐름은
[갱신안 서비스](../app/refresh/service.py), 입력·선택은 [선택 규칙](../app/refresh/selection.py),
후보·사실 검증은 [제안 검증](../app/refresh/validation.py)과 [사실 검증](../app/refresh/facts.py)을 확인했다.
전송 계약은 [모델 스키마](../app/adapters/llm_schema.py)와 [결과 직렬화](../app/refresh/serialization.py),
저장 경로는 [S3 어댑터](../app/adapters/refresh_artifacts.py)가 기준이다.
운영 연결 여부는 앱의 실제 조립 범위를 우선하며 Protocol·fake·테스트의 존재만으로 판단하지 않는다.

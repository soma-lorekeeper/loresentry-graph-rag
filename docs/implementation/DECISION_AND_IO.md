# 판단과 IO를 분리하는 구현 원칙

> **책임:** Python 유스케이스에서 순수 판단, 실행 조율, 실제 IO의 경계를 정한다.
>
> **확인할 때:** 새 기능을 구현하거나 기존 AI 코드를 이전하면서 함수·인터페이스·테스트를 나눌 때.
>
> **관련 문서:** 현재 모듈 배치는 [서버 구조](../ARCHITECTURE.md), 이전 범위는 [마이그레이션](../migration/overview.md), 테스트 실행은 [검증 계획](TEST_PLAN.md)을 따른다.

검증·계산·정책 판단은 필요한 값을 인자로 받아 결과를 반환하는 함수로 작성한다.
DB·HTTP·메시지·파일 접근은 별도 구현에 맡기고, 애플리케이션 서비스가 조회·판단·실행을 조율한다.
목표는 업무 규칙을 서버나 DB 없이 검증하고 운영과 테스트의 IO 구현을 교체할 수 있게 하는 것이다.

## 1. 선택한 방식과 적용 범위

Free Monad와 Algebraic Effects에서 가져온 아이디어는 판단과 실행의 분리다.
이 프로젝트에서는 일반 함수, 불변 dataclass, 필요한 Protocol과 의존성 주입으로 이를 구현한다.
범용 Effect Handler, 명령 해석 언어, 모든 IO를 표현하는 공통 명령 계층은 도입하지 않는다.

현재 적용 사례는 `GET /health/db`의 응답 검증과 내부 갱신안 생성이다.
갱신안 rules·서비스·JSON 결과 변환은 구현하고 fake IO로 검증했다. 실제 LLM·S3·Content·
Kafka 연결과 쓰기 트랜잭션 검증은 남아 있다. 아래 지침은 후속 어댑터에도 적용한다.

## 2. 책임을 나누는 기준

| 위치 | 담당 | 전달하는 값 |
|---|---|---|
| 순수 판단 함수 | 입력 검증, 계산, 정책 적용, 변경 필요 여부·내용 결정 | 스냅샷·설정·시각·ID를 받고 결과나 명시적인 실패 반환 |
| 애플리케이션 서비스 | 조회 순서, 판단 호출, 결정에 따른 실행, 실패 흐름 조율 | 필요한 최소 IO 인터페이스에 의존 |
| IO 어댑터 | DB 조회·저장, HTTP·LLM 호출, 파일·S3 접근, 메시지 발행 | 외부 응답을 내부 값으로 변환하고 알려진 기술 실패를 변환 |
| 조립 지점·웹 경계 | 환경 설정, 실제 구현 연결, 요청·응답 변환 | 외부 DTO와 내부 유스케이스 입력·결과를 매핑 |

순수 함수에는 DB 세션·HTTP 클라이언트·repository 객체를 넘기지 않는다.
이미 읽은 데이터를 넘기며, 입력 객체를 변경하거나 환경변수·전역 상태를 조회하지 않는다.
로그·메트릭 기록도 실행 쪽에 두고, 판단 근거가 필요하면 결과에 담아 전달한다.

시간이 정책에 영향을 주면 실행 쪽에서 얻은 `now`를 인자로 전달한다.
난수나 UUID가 필요하면 같은 방식으로 전달하되, 재시도에서 유지해야 할 작업 ID는 매번 새로 생성하지 않는다.
시간·ID 공급자를 교체할 필요가 실제로 생길 때 인터페이스를 추가한다.

## 3. 작업을 데이터로 표현할 때

`dataclass(frozen=True)`는 판단 결과나 실행할 작업의 의미를 명시하는 데 사용한다.
다음 조건에서는 구체적인 작업 타입을 고려한다.

- 판단 결과가 여러 변경으로 이루어져 실행 전에 내용을 검토해야 한다.
- 어떤 변경을 수행할지 서버 없이 비교·검증하는 것이 유용하다.
- 예상 revision, 작업 ID, 변경 내용을 실행 계층에 함께 전달해야 한다.

현재 `DocumentProposal`·`RelationProposal`은 대상 ID·기준 revision·제안 값·근거를 표현한다.
GraphRAG는 이 제안을 결과에 저장하며 원본에 적용하지 않는다. 사용자 확정 시 Content가
기준 revision과 관계의 현재 상태를 다시 검사해야 한다.
dataclass가 불변이어도 내부의 list·dict까지 자동으로 불변이 되지는 않으므로 입력 복사나 불변 컬렉션이 필요한지 판단한다.

조회 한 번과 결과 해석처럼 직접 호출로 충분한 흐름에는 작업 타입과 실행기를 추가하지 않는다.
저장·재생 요구가 없다면 명령 직렬화나 버전 관리도 미리 만들지 않는다.

## 4. IO 결과에 따라 다음 판단이 달라질 때

애플리케이션 서비스는 먼저 필요한 스냅샷을 조회하고 순수 함수에 전달한다.
판단 결과 추가 조회가 필요하면 그 IO를 실행한 뒤, 새 데이터로 다음 판단을 호출한다.
모든 작업을 첫 단계에서 하나의 계획으로 만들 필요는 없다.

판단에 필요한 정보를 IO 어댑터가 임의로 결정하지 않도록 한다.
반대로 연결 설정·전송·JSON 해석처럼 기술적인 처리는 순수 함수로 옮기지 않는다.
LLM 응답도 외부 IO 결과이므로 입력으로 받아 검증하며, 모델 호출 자체를 순수 판단으로 취급하지 않는다.

## 5. 현재 적용 사례

| 구분 | 구현 | 확인할 내용 |
|---|---|---|
| 판단 | [interpret_status](../../app/graph.py) | 객체·문자열 형식 검사, 누락 필드의 `unknown` 처리, `GraphStatus` 반환 |
| 조율 | [GraphHealthService](../../app/application.py) | 주입된 source 조회 후 순수 함수 호출, 결과 조립 |
| IO 계약 | [GraphStatusSource](../../app/application.py) | 상태 스냅샷 조회와 `GraphStatusUnavailable` 실패 계약 |
| 실행 | [NeptuneStatusSource](../../app/neptune.py) | HTTP 요청·JSON 해석·클라이언트 종료 |
| 연결 | [create_app](../../app/main.py) | 운영 어댑터 또는 테스트 대체 구현 주입, HTTP 매핑 |

이 사례의 dataclass는 실행 명령이 아니라 결과 값이다. 시간·난수·쓰기 작업이 없어 관련 공급자나 실행 계획도 없다.
운영은 `create_app()`으로 실제 어댑터를 연결하고 테스트는 `create_app(fake_source)`로 대체한다.
외부 라이브러리 구현을 상속하지 않아도 필요한 메서드를 제공하면 Protocol에 맞춰 연결할 수 있다.
구체적인 실패 응답과 조회 제한은 [제공 API](../API.md)와 [호출 API](../API_CALLS.md)에 둔다.

갱신안 사례의 순수 rules·여섯 IO 포트·실행 스냅샷·복구 경계는
[rules 이식 결과](../migration/rules-implementation.md)에 기록했다.

## 6. 트랜잭션·실패·재시도

판단과 실행을 분리해도 실행 시점의 상태 변경과 부분 성공은 남는다.
새 유스케이스에서는 다음 경계를 정한다.

| 상황 | 필요한 처리 |
|---|---|
| 조회 후 다른 요청이 데이터를 변경 | 저장 시 기대 revision 비교나 필요한 잠금으로 재검증. 충돌 시 재조회·재판단 또는 충돌 반환 |
| 같은 저장소 안의 여러 변경 | 함께 확정해야 하는 변경을 하나의 트랜잭션으로 묶음 |
| DB와 Kafka·S3·외부 API를 함께 사용 | 저장소별 성공 경계, 멱등 키, Inbox/Outbox 또는 복구 절차를 별도로 설계 |
| timeout·응답 유실 | 실행되지 않았다고 단정하지 않음. 같은 작업 ID로 결과 확인·재시도할 수 있는지 정의 |
| 중복 메시지·재실행 | 같은 이벤트의 중복과 서로 다른 이벤트의 순서 역전을 구분. 중복 키와 버전 비교의 책임을 결정 |
| 긴 계산 후 결과 저장·발행 실패 | 계산 결과를 재사용할지, 어디서 재개하고 완료 이벤트를 어떻게 재발행할지 결정 |

네트워크 대기나 LLM 계산 전체를 긴 DB 트랜잭션 안에 넣지 않는다.
트랜잭션을 여닫는 실제 처리는 저장소 어댑터가 맡되, 무엇을 함께 확정해야 하는지는 유스케이스에서 정한다.
재시도는 실패 종류·중복 안전성·횟수 또는 시간 예산을 정한 경우에만 적용한다.
예상한 업무 거절, 일시적인 IO 실패, 결과 불명, 코드 결함을 같은 실패로 뭉개지 않는다.

현재 상태 조회는 읽기 전용이며 자동 재시도가 없다. 반복 호출은 새로운 스냅샷을 읽을 뿐,
쓰기 멱등성이나 exactly-once 보장을 검증한 사례는 아니다.

## 7. 테스트와 마이그레이션 적용

순수 함수 테스트는 실제 서버·DB·외부 API 없이 입력과 결정 결과를 비교한다.
경계값, 거절 조건, 입력 불변성과 동일 입력의 동일 결과를 확인한다.
서비스 테스트는 대체 IO를 주입해 조회·판단·실행의 분기와 실패 시 후속 작업 중단을 검증한다.
통합 테스트는 실제 어댑터를 연결해 전송·저장·직렬화·자원 종료와 실패 변환을 검증한다.

현재 테스트 파일과 실행 명령, 실제 Neptune을 검증하지 않는 한계는 [검증 계획](TEST_PLAN.md)에 정리한다.
쓰기 유스케이스가 생기면 실제 저장소를 사용하는 트랜잭션·동시 변경·중복 실행 테스트를 추가한다.

기존 AI 코드를 이전할 때는 청킹·정규화·근거 병합에서 순수한 계산을 먼저 분리한다.
LLM·임베딩 호출, 검색·Neptune 저장, S3·Kafka 접근은 실행 구현으로 나누고 서비스에서 연결한다.
모든 파일에 인터페이스를 만들지 않고, 외부 부수 효과나 대체 구현이 필요한 경계에만 둔다.
이전할 기능과 아직 정하지 않은 계약은 [마이그레이션 범위](../migration/overview.md)가 기준이다.

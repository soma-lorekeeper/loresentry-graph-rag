# Refresh 갱신안 생성

`RefreshService`는 조회·모델·저장 포트와 `RefreshRules`를 생성자로 주입받는다.
기본 rules는 입력·선택·청킹·문맥·후보 검증을 수행한다. OpenAI 어댑터는 별도 평가
스크립트에서 주입한다. [S3 저장소 어댑터](../../docs/implementation/S3_ARTIFACTS.md)도
서비스에 주입할 수 있다. Neptune 원홉·완료 Inbox와 Content HTTP 어댑터도 구현했다.
기본 평가는 fake IO를 사용한다. 실제 Kafka 수신과 완료 Outbox relay는 업무 runtime에 연결돼 있다.
복구는 [완료 Inbox와 S3 재사용](../../docs/implementation/REFRESH_INBOX.md)을 따르며
별도 작업 상태 저장소·lease 없이 `run(request)`를 호출한다.

처음 읽을 때는 `models.py`에서 값의 의미를 보고, `rules.py`의 판단 단계를 확인한 뒤
`service.py`의 조회·판단·실행 순서를 읽는다. `ports.py`는 실행 구현이 지킬 계약이다.

| 파일 | 책임 |
|---|---|
| `selection.py` | 입력 범위·manifest 검증, 부족한 본문 ID 선택, 스냅샷 확정 |
| `evidence.py`, `../text/chunking.py` | 원문 구간 분할과 근거 중복 제거 |
| `context.py`, `prompts.py` | 결정적 출처·문맥·프롬프트 구성과 예산 확인 |
| `prompt_versions.py` | 실제 생성에 허용한 프롬프트 버전과 v11·v12 비교 기준선과 v13 작업 계획 버전 |
| `validation.py` | 문서·관계 후보 검증, 중복·충돌·NO_CHANGE 판정 |
| `facts.py` | 복원한 원문에서 구조화 사실의 행동·역할 표현·문서/제안 참조 검사와 관계 설명 조립 |
| `repair.py` | 구체적 검증 진단·실패 후보를 같은 문맥에 넣는 최대 2회 보완 입력과 예산 검사 |
| `workflow.py`, `workflow_prompts.py` | 문단 ID 계획 검증, 작성 범위, 원문 보존 조립 |
| `serialization.py` | 결과 JSON과 완료 이벤트 값으로 순수 변환 |
| `service.py` | IO 순서·다중 호출·저장·Inbox/Outbox 기록·복구 조율 |
| `outbox.py` | 미발행 완료 전송·확인·재시도 |

판단 함수는 포트를 호출하지 않는다. 추가 자료가 필요하면 ID를 반환하고 서비스가 조회한
결과를 다시 전달한다. 시간·난수·환경변수도 순수 함수에서 조회하지 않는다.

기본 `ModelSettings`는 `refresh-prompt-v13`·`refresh-candidate-v7`의 두 단계 경로다.
첫 호출은 `refresh-plan-v1` 계획을 반환한다. 서버가 설정 본문을 원문 위치를 보존한 문단으로
나누고 P0001 등 ID를 붙인다. 계획은 검토한 문서 ID 전체와 문단 REPLACE·DELETE·APPEND,
신규 설정 후보, 새 관계 및 변경 원고 마커를 지정한다. 원고·문서 자체·기존 관계 삭제는 없다.

두 번째 호출은 계획의 모든 edit_id에 대한 text·fact_ids, 계획된 신규 설정과 관계,
구조화 facts를 반환한다. 서버는 각 수정본을 지정 문단에 적용하고 나머지 본문·공백은
원문 그대로 유지한다. 모르는 ID·revision, 중복 작업, 계획 누락·추가, 미수정 교체,
현재 변경 원고 밖 출처를 거절한다. 호출 두 단계가 전체 대상 문서를 함께 보며 별도 discovery는 쓰지 않는다.

계획과 작성에 걸쳐 보완은 전체 한 번이다. 계획·작성의 두 최초 호출과 보완 한 번을
합쳐 최대 세 번이고, 요청의 호출 예산이 더 작으면 그 예산을 따른다. 계획 보완을 사용하면
작성 보완을 추가하지 않는다. 결과의 execution.change_plan과 attempts.stage에
계획·작성·보완 내역을 저장하며 완료된 같은 요청의 재실행은 모델을 다시 호출하지 않는다.

v5·v6 및 v11·v12는 과거 응답과 평가 비교를 위해 유지한다. 이 한 단계 경로에서는
기존 대상별 호출·최대 두 번 보완 정책을 사용한다. 이전 평가용 기대 fixture도 이 경로에
명시적으로 고정한다. v13·v7 요청은 실제 RefreshService에서 두 단계로 동작한다.

실제 두 단계 평가는 `scripts.evaluate_refresh --two-stage --live`로 실행한다.
`--confidence`를 함께 쓰면 작성 계약은 v8이며 각 fact의 0∼1 confidence를 관찰한다.
한 단계 평가에서는 같은 옵션이 v6을 선택한다. 자기평가 점수는 certainty와 구별하며,
사실 ID·내용 비교·제안 채택에는 사용하지 않는다. 계획 단계에는 사실 점수가 없으므로
출처·confidence 관찰에서 not_applicable로 표시하고 작성 결과와 합산하지 않는다.

계획된 작업을 모두 수행했는지는 검사하지만, 모델이 첫 계획에서 관련 위치를 빠뜨리거나
수정 문단 안의 뜻·기존 사실을 잘못 바꾸는 가능성은 남는다. 의미상 완전성과 교체 품질은
[실제 소설 평가](../../docs/migration/refresh-quality.md)에서 별도로 확인한다.

`SelectionSettings.chunk_overlap_chars`는 기본 0이다. 0이면 과거 청크·직렬화를 유지하고,
양수는 `chunk_chars`보다 작은 정수만 허용한다(bool은 거절). 이전 청크의 완전한 문장을
한도와 여유가 있을 때 다음 청크에 겹치며, 여유가 없으면 생략한다. 문장부호·줄바꿈 경계와
과대 문장 분할을 사용하고 원문 위치·전체 덮기·청크 크기·전진을 보존한다. 근거 검증도
동일 설정으로 청크를 재생성하고, 겹친 텍스트를 포함한 문맥에 예산을 적용한다.

한 단계 v5·v6 후보에 구체적 검증 진단이 있으면 서비스가 같은 범위에서 최대 두 번 보완한다.
출처·역할·사실 참조의 오류에 필드 경로와 규칙을 전달하며, 원문과 후보를
`repair-v2`에서 오류 사실을 특정할 수 있는 역할 문서 참조
진단은 무관한 제안과 참조 사실을 이전 후보에서 보존한다. 오류 사실을 참조한 제안은
보완 응답을 사용하고 병합 후보 전체를 다시 검증한다. 파싱·전역 오류는 전체 후보를
보완하며, 이전에 통과한 호출은 반복하지 않는다. 추가 시도에도 호출·문맥·어댑터 토큰 예산을 적용하며 남은 최초
호출을 예약한다. 전체 통합 실패와 연동·인증·설정 오류는 자동 보완하지 않는다.
보완 실패는 제안 없는 최종 FAILED이며 저장된 FAILED도 동일 요청에서는 그대로 재사용한다.

Responses 어댑터는 seed 설정을 제공하지 않고 `reasoning.effort`도 생략하여 기본
`medium`을 유지한다. 실제 `gpt-6-luna` smoke는 v11의 record-and-consent 한 사례에서
4회 호출·보완 1회 성공 뒤 `PROPOSED`였지만 의미·자유 본문은 사람 검토 대기다.
반복 의미 평가에서도 v12의 우세는 확인하지 못해 당시 비교 기준선 v11을 유지했다. 현재 기본 두 단계 v13의 결과는 별도 소설 평가로 기록한다.
현재 설정 예시의 출력 예산은 32,768토큰, 입력은 922,000토큰(호출당 예산은 그 80%),
문맥은 1,050,000토큰, timeout은 240초이며,
일반 의미 품질은 [실제 비교 기록](../../docs/migration/refresh-quality.md#6-luna-실제-비교-기록)을 따른다.

[반복 비교 CLI](../../scripts/evaluate_refresh_ab.py)는 v11·v12를 각각 최소 2회 독립 실행하고
선택적으로 v12의 문장 겹침 조건도 비교한다. 보완을 포함한 자식 전체 호출 예산을 미리
예약한다. 비교 요약은 원문·제안 본문·공급자 오류 없이 수치와 상태만 0600 권한으로
저장하며 사람 의미 검토를 남긴다. 명령과 전체 상한 계산은
[어댑터 사용법](../../docs/migration/openai-adapter.md#프롬프트와-청크-겹침-반복-비교)을 따른다.

## 원문 표현 정책

사실의 action·surface·statement는 원문 문자열과 대조하지 않는다. 모델이 원문 표현을 바꿔 써도
그것만으로 실패하지 않으며 서버가 표현을 고치지도 않는다. 사실 검증은 출처 마커가 서버 청크와
일치하는지, 역할 문서 ID가 존재하고 프로젝트 범위인지, 필드 길이·분류 값과 제안의 사실 참조를 본다.
역할·부정·조건·범위 보존은 프롬프트와 품질 평가에서 확인한다.
작성 단계 본문이 계획의 문단 조립 결과와 다르면 실패하지 않고 서버 조립 결과를 사용한다.
이전에 저장된 결과의 `source_alignments`는 읽을 때 무시한다.

계획의 source_markers는 우선 확인할 근거다. 작성은 입력의 다른 변경 원고 마커를
참조할 수 있으며 execution.source_scope_extensions에 추가 사용 위치와 마커를 기록한다.
현재 변경 원고 밖의 근거는 허용하지 않는다. 계획의 문단·신규 후보·관계 목록은 그대로 고정한다.

문단 ID는 줄마다 붙인다. Content는 에디터 블록을 줄바꿈 하나로 이어 평문을 만들기 때문이다.
APPEND는 문서가 쓰는 줄바꿈(빈 줄 또는 줄바꿈 하나)을 따른다.

계획과 작성 결과의 기계적인 실수는 실패 대신 서버가 고치거나 버린다(`tolerance.py`, `workflow.py`).
- 계획: 잘못된 문단·마커·범위 밖 작업은 버리고, 같은 문단의 작업은 하나로 합치며, 기존 설정과 이름이
  같은 신규 설정과 허용되지 않은 관계는 버린다. 옮겨 적다 몇 글자 틀린 문서 ID는 가장 가까운 실제 ID로
  고친다. 방향만 다른 관계는 합치고, 신규 설정과 그 근거 원고의 관계가 없으면 채운다.
- 작성: 빠지거나 근거 사실이 없거나 내용이 바뀌지 않은 문단 작업은 그 문단을 원문대로 둔다. 계획에
  없는 신규 설정·관계는 버리고, 빠진 것은 제안하지 않는다. 신규 설정 근거에는 참조한 사실의 출처를 더하고,
  관계 키와 기준 revision은 끝점의 유형·revision으로 채우며, 거의 같은 사실은 한 번만 참조한다. 계획한
  원고 연결을 작성이 빠뜨리면 신규 설정의 사실로 만든다.
- 본문에 옮겨진 작성 지시·확인 단서 문장('~단정하지 않는다', '원고에서 확인되지 않는다' 등)은 지운다.
  지울 문장만 남은 본문은 그대로 둔다.
- 사실의 문서 ID가 틀렸으면 가장 가까운 ID로 고치고, 가까운 ID가 없을 때만 보완 대상이 된다.
저장 결과의 제안은 계획의 부분집합이면 된다.

작성 응답이 서버가 그대로 보존할 같은 문서의 문단을 완전히 복사한 경우 해당 복사본만
제거한다. 변경·삭제 대상 문단, 다른 문서, 유사 표현과 부분 복사는 제거하지 않는다.
execution.paragraph_copy_removals에는 edit_id, 원문 문단 ID와 제거 전 작성 text를 기록한다.
문단의 의미를 추정해 수정하거나 무관한 기존 사실을 삭제하는 처리는 아니다.
